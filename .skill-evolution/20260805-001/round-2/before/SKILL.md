# 长篇网文创作工作流

这是长篇连载小说的总控 Skill。目标不是一次产出大量文字，而是稳定地把读者承诺、因果、状态、伏笔与章节体验连接成可持续生产的系统。

总控担任主编与生产总监：先诊断项目状态，再调用专项子 Skill、组织编辑会诊与用户决策、维护 Canon 提交边界、调度可恢复的生产链。它不替代专项创作，也不把候选方案写成既定事实。

## 三项核心原则

1. 读者体验优先：每卷兑现一个明确承诺；每章都发生可见变化，并留下继续阅读的理由。
2. Canon 优先：已确认的世界规则、秘密、角色状态、时间线和伏笔是唯一事实源。新内容先是候选，批准后才提交。
3. 先计划后写作：正文必须建立在已锁定细纲和最小必要上下文上；连续剧情默认串行写作。

## 30 秒调度：先给运行卡，再展开流程

不要把一次局部请求展开成 1–150 步的复述。每次只执行与当前请求匹配的最小路径：

1. **判定状态**：新项目进入初始化；已有项目先诊断；只有灵感进入定位；改设先影响追踪；正文进入受控生产。
2. **读取最小输入**：项目目录、用户意图、目标章节/Canon ID，以及当前 Canon 版本；没有项目目录时，只收集信息，不创建文件。
3. **输出运行卡**：列出 `首要子 Skill`、`读取文件`、`写入目标`、`验证命令`、`停止条件` 与 `下一位责任人`。未满足前置条件时，运行卡只给恢复动作。
4. **执行一条路径**：先读取运行卡指定的子 Skill；完成后报告产物与状态，不并行启动无关席位。

运行卡模板：

| 字段 | 必填内容 |
|---|---|
| 请求与状态 | 用户目标、新建/继续/改设/修复、项目目录 |
| 路由 | 一个首要子 Skill；需要会诊时列出顺序，不并列提交权 |
| 输入与写入 | 必读 Canon/细纲/正文；允许写入的候选区或目标文件 |
| 验证与恢复 | 必跑命令、失败后的下一动作、恢复入口 |
| 停点 | 必须由用户确认的决定，或可由授权档位自动处理的范围 |

## 先判断项目状态

| 用户请求 | 进入路径 | 首要子 Skill |
|---|---|---|
| 从任意章节/卷继续、修复、改设、审计或发布 | 项目诊断 | project-diagnosis |
| 新项目、初始化、参数、框架或追踪模板 | 项目初始化 | project-bootstrap |
| 只有灵感、选题或一句话梗概 | 选题确认 | story-positioning |
| 需要专业资料、平台信息或现实知识 | 调研（可选） | story-research |
| 世界、体系、势力、角色、悬疑设计 | 核心设定 | 对应设定子 Skill |
| 全书、长线、分卷或章节规划 | 大纲与细纲 | 对应规划子 Skill |
| 自动推进 1–10 章、批量写作或恢复中断批次 | 受控批次生产 | serial-production |
| 写、续写、改写某章 | 单章生产 | chapter-drafting |
| 查设定、查时间线、查伏笔、处理吃书 | Canon 治理 | canon-management |
| 全书 Review、最终质检或项目交付 | 全局审计与交付 | global-review、manuscript-quality-audit 或 project-delivery |

对新项目，先运行参数估算与初始化。它们只创建缺失文件，不覆盖现有作品：

    python scripts/calculate_parameters.py --total-words 800000 --genre 悬疑
    python scripts/init_story_project.py --project-dir path/to/project --title 暂定书名 --genre 悬疑 --target-words 800000

读取 [项目文件契约](references/project-files.md) 后再写入项目。文件含义、状态和命名以该契约为准。

立项后可按题材选择 [题材包](references/genre-packs.md) 作为检查表，并把符合本项目的约束写入 brief.md；场景、钩子、爽点和反转的共通方法见 [连载工艺工具](references/craft-patterns.md)。题材包不能覆盖已确认的读者承诺或 Canon。

将现有子 Skill 当成编辑团队席位，而非互相独立的提示词。总编、故事架构、人物、连载、连续性、文字与生产岗位的职责和会诊规则见 [创作团队职责](references/editorial-board.md)；流行长篇的章节、人物、卷级和修订判断见 [编辑标准](references/editorial-standards.md)。

## 可恢复调度与显式停点

先运行诊断或初始化，再写入项目。遇到下列触发条件时，停止当前路径并按表恢复；不得以手工改文件跳过状态机。

| 触发条件 | 一线修复 | 仍失败时的兜底与恢复入口 |
|---|---|---|
| 缺少项目目录、目标章节或 Canon ID | 请求最小缺失信息；不创建目录、不猜测项目状态 | 输出 manual 运行卡，等待用户补齐信息后从步骤 1 重启 |
| `diagnose_project.py` 报 blocker | 将 blocker、影响文件和前置条件写入运行卡，只调用推荐的修复子 Skill | 修复后重新运行同一诊断；blocker 未清零时禁止写正文或提交 Canon |
| 改设没有 `changed-id`、影响追踪缺失或结果不完整 | 运行 `trace_canon_impact.py`，补齐受影响的 Canon、细纲、正文与迁移计划 | 无法追踪时保持候选状态，转为用户决策；不得直接覆盖既有 Canon |
| Canon 版本与锁定细纲、上下文包或批次状态不匹配 | 重基细纲并重新编译上下文；由 `batch_controller.py` 校验下一状态 | 状态仍异常时记录 halt 原因，运行 regression suite 后从控制器 `next` 恢复 |
| 脚本、文件契约或子 Skill 缺失/报错 | 报告命令、错误和受影响文件；仅做只读诊断与最小修复计划 | 不能验证时停止写入，交给用户决定补齐资源、改走 manual，或终止本批次 |
| 审校出现 S1/S2、未批准新事实或作者决策 | 停在候选/审校状态，列出证据、影响范围和可选方案 | 用户确认后由对应席位处理；未经确认不得锁定章节或提交 Canon |

**🔴 CHECKPOINT 1 — 首次写入前：** 新项目的定位、核心读者承诺、项目目录和授权档位必须由用户确认；否则只写候选和运行卡。

**🔴 CHECKPOINT 2 — Canon 变更前：** 世界规则、结局、重大关系、角色核心选择或既有 Canon 的改设，必须展示影响追踪与迁移方案，等待用户确认。

**🛑 STOP — 批次自动推进：** 出现 blocker、S1/S2、版本不匹配、未锁定细纲、未批准新事实、资源异常或用户暂停时，控制器立即 halt；修复后只能从 `batch_controller.py next` 恢复。

## Canon 与决策边界

Canon 是可追溯的已确认事实集合，位于项目的 正典 目录。包括世界、力量、势力、谜案、角色、关系、情绪承诺、当前状态、时间线、伏笔台账与 registry.json。

- 候选方案写入各文档的“候选 / 待确认”区，不能作为后续正文依据。
- 只有 canon-management 可在用户确认或明确授权后，把候选内容提交为 Canon，并记录理由、影响范围、版本和责任章节。
- 改写既有 Canon 必须先做影响追踪：受影响章节、角色知识边界、伏笔、细纲、正文与需要补写的迁移方案。
- 用户保留定位、主角核心选择、结局、重大关系与最终文风的决定权。没有确认时，保留 2–3 个差异清晰的候选方案。

## 高风险行动黑名单

下列行为会破坏可追溯性或作者控制权，禁止执行：

- 不得把候选、推测、审校建议或未验证资料写成 Canon、既定剧情或角色已知事实。
- 不得绕过影响追踪改写既有 Canon，也不得只改正文而不登记受影响的细纲、伏笔、时间线与角色知识边界。
- 不得并发起草相邻连续章节，或在上一章未 locked 前启动下一章。
- 不得根据目录中现有文件数量推断生产状态，或手工跳过 `batch_controller.py` 的状态转换。
- 不得调用不存在的子 Skill、让多个席位争夺 Canon 提交权，或在脚本失败后静默继续。
- 不得以对标作品的可识别情节、人物或文风替代原创设计；调研与平台规则未经核验不能当作事实。
- 不得在没有用户授权时自行决定定位、结局、重大关系、主角核心选择或最终文风。

## 从任意节点开始

## Windows 脚本运行约定

在 Windows PowerShell 中运行会再启动 Python 子进程的工作流脚本前，先设置一次 UTF-8 输出环境；否则父进程以 UTF-8 读取中文诊断时可能中断：

    $env:PYTHONIOENCODING='utf-8'

此设置只影响当前 shell 会话。若脚本仍失败，按“脚本、文件契约或子 Skill 缺失/报错”的恢复规则记录命令、编码错误和受影响文件；不得跳过状态机继续写作。

不要假设项目从步骤 1 顺序完成。对于续写、补设定、重写、项目中断、全书审计或发布，先运行：

    python scripts/diagnose_project.py --project-dir path/to/project --intent continue

诊断输出 blocker、Canon 版本、批次状态、受影响文件、推荐席位和恢复路径。改设附加 `--intent revise --changed-id canon.id`；修复后运行 regression suite。控制平面与不变量见 [控制平面](references/control-plane.md)。

## 阶段 0：项目初始化（步骤 1–15）

调用 project-bootstrap。它先计算篇幅、卷数、题材、平台约束和“读者承诺潜力”风险评估；后者是可持续冲突、差异化、兑现引擎与生产风险的诊断，不承诺“爆款”。

步骤 1–15 必须完成：项目参数、目录、旧 story-long-write 路由替换、10 份核心参考资料、角色关系/伏笔/情绪/力量/世界/悬念六类框架、核心设定表、四类追踪模板、大纲/卷纲模板、全局一致性清单与完成确认。详细的不可丢失映射见 [步骤总表](references/step-map.md)。

旧名 story-long-write 不是仓库实际能力，必须路由为 chapter-drafting + chapter-editing + canon-management + serial-production；禁止调用不存在的 Skill。

阶段 0 的门禁：运行 validate_global_framework.py 后无结构缺口；所有框架都明确“候选 / 已确认 / TBD”状态，不能把框架草图冻结为 Canon。

## 阶段 1：选题方向确认（步骤 16–30）

调用 story-positioning，必要时调用 story-research。完成用户输入分析、目标情绪、题材/题材包、平台、读者、对标作品（如用户提供）、核心卖点、核心梗三分法、微创新、定位文档、3–5 个书名、简介与用户确认。

对标只分析读者承诺、冲突引擎、节奏和差异化空间，不复制情节、人物或可识别文风。没有用户确认时，定位和书名/简介均为候选；确认后更新 genre-positioning.md 与 approvals.md。

## 阶段 2：核心设定（步骤 31–75，不得跳过）

本阶段目的：填充世界观、力量体系、势力、角色等所有核心设定。各层产出先经冲突检查，再由 canon-management 汇总提交。

### 层次 1：世界观基础（31–34）

调用 world-design，完成：

31. 设计时代背景；
32. 设计社会结构；
33. 设计核心设定、不可违背因果与代价；
34. 创建并校验世界观文档（地理、资源、技术与日常秩序随前三项归档）。

### 层次 2：力量体系（35–37）

调用 power-system-design，完成：

35. 等级、门槛与可观察的差异；
36. 能力、资源、训练与对抗关系；
37. 限制、代价、失控条件和反制路径。

没有成本、反制与信息边界的能力不能冻结为 Canon。

### 层次 3：势力（38–45）

调用 faction-design，完成：

38. 设计势力分布、资源与组织结构；
39–41. 并行提出默认 3 个正道/秩序方候选；
42–43. 并行提出默认 2 个中立方候选；
44–45. 并行提出默认 2 个反派势力候选并统一合并。

世界基础冻结后，力量、势力与谜案可并行提出候选；它们不得并行修改同一 Canon 事实，必须由总控顺序合并。

### 层次 4：悬疑元素（46–49）

调用 mystery-design，完成：

46. 谜案类型与全书核心问题；
47. 线索、证据、误导与可推理机制；
48. 超自然或特殊规则怎样参与而不替代推理；
49. 悬念系统、揭示窗口和答案的因果闭环。

### 层次 5：角色（50–67）

调用 character-arc-design，完成：

50. 主角基本信息；51. 性格特点；52. 核心机制/金手指及其限制；53. 核心动机；54. 背景故事；55. 成长弧线；56. 创建主角设定文件。
57–63. 按 workflow-config 的数量（默认 7）并行提出配角候选，按功能、独立欲望、知识边界和出入场窗口合并；
64. 幕后大 Boss；65. 2–3 个中期反派候选；66. 3–5 个前期反派候选；67. 关系网络、知识边界、冲突触发器与可变关系。

### 层次 6：情绪与差异化（68–75）

调用 reader-experience-design，完成：

68. 更新设定表与读者承诺；
69–70. 设计主情绪、情绪曲线、压抑与释放的比例；
71–72. 设计爽点、代价、反噬与兑现节奏；
73–74. 设计差异化、题材混搭边界与记忆点；
75. 汇总创作要点、禁区、风险和首卷验证问题。

阶段 2 的门禁：所有 31–75 项均有“已确认、候选、TBD 或不适用”的明确状态；没有静默遗漏。详见 [Canon 文件契约](references/project-files.md)。

## 阶段 3：大纲搭建（步骤 76–108，不得跳过）

目的：搭建全书卷级结构和宏观框架。每一个“反转”都必须改变人物的行动空间、代价或读者理解，而不是只隐藏信息。

### 层次 1：全书宏观框架（76–78）

调用 series-architecture，完成：

76. 卷级结构、各卷读者承诺和状态迁移；
77. 主线谜案 / 核心冲突的推进链；
78. 信息与真相的揭示节奏。

### 层次 2：全书系统（79–87）

调用 long-arc-planning，完成：

79. 全书情绪弧线总图与压力递进；80. 全书爽点节奏、代价与阶段兑现；81. 主角全书成长弧线；
82. 并行提出关键配角全书成长弧线；83. 并行提出反派全书演变过程；
84. 长期伏笔目标（300+ 章项目默认 30–50 条，按可追踪能力调整）；85. 中期伏笔；86. 短期伏笔；87. 反转点、前置证据、影响与后果。

### 层次 3：各卷详细设计（88–102）

调用 volume-planning，对每卷固定执行三步：详细规划、情绪弧线、爽点节奏；根据前卷状态动态调整。为保证步骤 88–102 可审计，默认按三步一组登记：88–90 为第 1 卷、91–93 为第 2 卷、94–96 为第 3 卷、97–99 为第 4 卷、100–102 为第 5 卷。少于五卷时把未用组标为“不适用”；多于五卷时继续沿用“详细规划—情绪弧线—爽点节奏”循环，并在总纲说明扩展映射。不能只详细规划第一卷而把其余卷留为空标题。

每卷至少有：入卷状态、读者承诺、对手压力、中段反转、卷末兑现、出卷新债、关联角色、伏笔与情绪节奏。

### 层次 4：文档创建（103–108）

调用 canon-management 与 build_story_docs.py，完成：

103. 创建/更新全书总纲；104. 创建第 1 卷卷纲；105. 创建第 2 卷卷纲；106. 创建第 3 卷卷纲；107. 创建第 4 卷卷纲；108. 创建第 5 卷卷纲，并登记章节索引、伏笔/状态映射、版本和待确认项。少于五卷标为不适用，超过五卷继续创建并登记扩展映射。

阶段 3 的门禁：全书每卷都有可执行的进入和退出状态；角色弧线、伏笔、反转与卷纲能互相追溯。

## 阶段 4：细纲设计（步骤 109–118，不得跳过）

目的：为全书每一章设计细纲。调用 chapter-outline，并用 validate_outline.py 做覆盖与字段检查。

109. 创建细纲目录与章节索引；
110. 计算全书章节数、卷章范围与批次；
111–113. 先完成第 1–30 章的校准批次，验证首章钩子、文风、承诺与节奏；
114–117. 按最多 100 章的规划批次覆盖剩余章节，逐批审计、合并、修订与锁定；
118. 确认全书章节均有计划细纲，记录缺口、TBD 和锁定范围。

每章细纲必须包含以下全部字段：章节定位、入章状态、核心事件与因果、4–8 个场景节拍、情绪目标/曲线/强度、章首钩子、爽点及代价、伏笔操作、角色状态变化、章尾钩子及后继责任、字数/场景预算、Canon 冲突检查。最低的六项刚性要求是：核心事件、情绪目标、章首钩子、章尾钩子、爽点设计、字数目标。

并行只允许在同一 Canon 快照上制作互不重叠的候选细纲；合并和锁定必须串行。相邻连续章节的正文不得并行起草。详见 [并行与合并规则](references/parallel-execution.md)。

## 阶段 5：全局 Review（步骤 119–125）

调用 global-review，依次由故事架构、人物、连载、连续性与文字席位审计全书大纲、各卷卷纲、所有细纲、伏笔系统、角色设定和世界观设定，并输出全局 Review 报告。发现问题先分类为 Canon、结构、章节执行或作者决策；不能用“整体还不错”跳过某一项。

阶段 5 的门禁：每个审计对象有结论、证据、影响范围、责任步骤和处理状态。任何 S1 阻断问题必须在进入正文前清零。

## 阶段 6：正文写作（步骤 126–135，动态扩展）

调用 serial-production，先诊断后使用 batch_controller.py 与 orchestrate_batch.py 逐章串行推进。其批次为：第 1 章示范与审校；第 2–10 章与批次审校；第 11–50 章与批次审校；第 51–100 章与批次审校；其后每个不超过 100 章的连续批次。

“自动写 1–10 章”可以执行，但不是并发生成十章：编排器为每一步生成“席位、输入、写入目标、验证命令”的任务卡，控制器逐章执行“重基细纲 → 上下文 → 正文 → 编辑 → Canon 提交 → 锁定”，每次都持久化检查点。它会在 S1、Canon 冲突、缺失锁定细纲、未批准的新事实、需要作者决定或上下文缺口时自动暂停。用户明确授权后，可自动处理已锁定细纲内的常规状态变化；世界规则、结局和重大关系仍须停下确认。

## 阶段 7：最终质量检查（步骤 136–145）

调用 manuscript-quality-audit：创建最终检查目录，并行进行全书情绪交付审读、技术质量检查、用户配置禁用项扫描、机械化表达/重复结构诊断；随后更新全部追踪文件，生成全书质量报告、总结报告和文件清单，等待项目完成确认。

禁用项扫描只使用作者/平台给出的词表或规则；“去 AI 味”只能是带位置和模式证据的机械化表达诊断，不能声称存在可靠的 AI 文本检测器。

## 阶段 8：输出与展示（步骤 146–150）

调用 project-delivery：最后更新上下文、伏笔、时间线、角色状态，生成总结报告，展示项目清单和未决项。可选调用 publication-packaging 准备发布材料；平台规则、审核要求和 AI 内容标记必须先经 story-research 核验。

## 子 Skill 路由

| 子 Skill | 职责 |
|---|---|
| story-positioning | 立项、受众、卖点、定位与项目简报 |
| project-bootstrap | 步骤 1–15 的参数、框架、模板、参考资料与一致性门禁 |
| project-diagnosis | 从任意节点诊断、恢复、改设影响与安全路由 |
| story-research | 事实调研与创作转化（可选） |
| world-design / power-system-design / faction-design | 阶段 2 的世界、力量、势力 |
| mystery-design / character-arc-design / reader-experience-design | 阶段 2 的谜案、角色、情绪与差异化 |
| series-architecture / long-arc-planning / volume-planning | 阶段 3 的全书、长线与分卷设计 |
| chapter-outline | 阶段 4 的全书细纲与章节锁定 |
| chapter-drafting / chapter-editing | 正文起草与编辑审校 |
| canon-management | Canon 变更、冲突、版本、状态和伏笔 |
| global-review / serial-production | 全局 Review 与可恢复的串行批次生产 |
| manuscript-quality-audit / project-delivery | 最终审计、报告、展示与交付 |
| serial-review / publication-packaging | 周期复盘与发布（后者可选） |

在对应任务前读取相应子 Skill。不要调用仓库不存在的代理或把多个子 Skill 的提交权混为一谈。

## 完成标准

完成任一阶段时，报告：已完成的步骤与文档、Canon 当前版本、未决项、风险、下一步和需要用户确认的决定。只有所有必要步骤被覆盖、质量门禁通过、文件索引已更新且没有未说明的事实冲突，才可以宣称该阶段完成。

## 工作流自审

在阶段完成、批次 halt、发现连续性问题或用户反馈流程缺陷后，先记录项目级问题，再运行：

    python scripts/audit_workflow_skill.py --skill-dir path/to/story-workflow

它检查 1–150 步骤映射、路由、子 Skill 与关键工具是否齐全。项目级修复后再运行：

    python scripts/run_regression_suite.py --project-dir path/to/project

随后按 [工作流持续自审](references/workflow-maintenance.md) 复现和修复；未经用户要求，不自动改写这个 Skill 或项目 Canon。
